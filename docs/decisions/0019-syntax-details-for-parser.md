# ADR-0019: 括号里的续行、修饰符顺序、区间优先级、错误码前缀

- 状态：已接受
- 日期：2026-10-06

## 背景

第十四轮讨论。开始写 Parser 时，有四处细节在 ADR-0005 到 0017 里没有写死，Parser 必须选一种：

- ADR-0013 说“二元运算符写在行尾是编译错误”，但圆括号、方括号里的换行本来就不结束语句，没说那里算不算。
- 一个声明可以带好几个修饰符，没规定顺序。
- 区间 `..<` / `...`（ADR-0010）和算术运算混写时怎么分组。
- 诊断要带稳定的错误码（ADR-0003），前缀没定。

和用户对比代码后，四项都按推荐定了。

## 决策

1. **运算符一律放在行首，括号里也一样**。二元运算符（包括 `and`、`or`、`??`、`is`、`as`、`..<`、`...`）以及 `.`、`?.` 写在行尾都是编译错误，诊断提示挪到下一行开头。允许写在行尾的仍然只有 `=` 和 `->`（ADR-0013），ADR-0020 又加上了 `+=` 等复合赋值。
   ```nyxel
   let d = Vector3.Distance(
       self.Position
           + offset,            // 正确
       target)

   let e = Vector3.Distance(
       self.Position +          // 错误：把 + 挪到下一行开头
           offset,
       target)
   ```
2. **修饰符顺序固定**：可见性（`public` / `protected` / `private`）→ `static` → `abstract` / `sealed` / `virtual` / `override` → `async`。这一组里出现两个时 `override` 写在最后（`sealed override`、`abstract override`，组合是否合法同 C#）。顺序不对、同一个修饰符写两次都是编译错误，诊断给出正确的写法。
   ```nyxel
   public static var Killed: int = 0          // 正确
   protected override func OnEnable(self) {}  // 正确
   public override async func Run(self) {}    // 正确
   static public var Killed: int = 0          // 错误：写成 public static
   ```
3. **区间的优先级比算术低、比比较高**（Swift 的做法）：两边先把 `*` `/` `%` `+` `-` `<<` `>>`（和比它们更紧的 `as`、一元运算、成员访问）算完，再组成区间。比较、`is`、`and` / `or`、`??` 要写在区间两边时加括号。区间不能连写（`a..<b..<c` 是错误）。
   ```nyxel
   for i in 0..<self.count - 1 { }      // 0 ..< (count - 1)
   for i in self.start + 1...self.end * 2 { }
   ```
   完整的优先级从高到低：成员访问、调用、下标 → 一元（`-` `+` `~` `not` `await` `launch`）→ `as` → `*` `/` `%` → `+` `-` → `<<` `>>` → `..<` `...` → `<` `>` `<=` `>=` `is` → `==` `!=` → `&` → `^` → `|` → `and` → `or` → `??`。除了 `as`（ADR-0014）和区间，其余同 C#。
4. **错误码是 `NYX` 加四位数字**，比如 `NYX1103`。按编译阶段分段：`NYX1xxx` 是词法和语法错误，`NYX2xxx` 起留给语义分析。段内按添加顺序编号，新错误码取这一段当前最大的号加一，不再按类别细分（类别写在 design/diagnostics.md 的表里）。错误码一经发布不再改变含义，删掉的错误码也不重用。

## 备选方案

- 括号里的续行：**只在会结束语句的地方报错，括号里随便**（Python）：括号里没有歧义，少一条限制；但同一件事有两种写法，要靠格式化器统一，读者也要分两种情况记规则。
- 修饰符：**任意顺序（C#），由格式化器统一**：编译器不用管，但没格式化过的代码里顺序各不相同。**任意顺序，不对时给警告**：不挡编译，但仍是两种写法都能通过。固定顺序时 Agent 照诊断改一次就对。
- 区间：**比乘除还高**（C# 的 `..`）：和 C# 一致，但 `0..<self.count - 1` 会被读成 `(0..<count) - 1`，是很容易写错的写法，要加括号才对。
- 错误码：**`NX`**：和 CS / FS / TS 一样两个字母，但 NX 撞名多（Siemens NX、Nx 构建工具），不好搜。**`NYXEL`**：最不会混淆，但每条都长一截。

## 后果

- 行尾运算符的检查在 Parser 里做，不区分是否在括号里；诊断都给出挪到下一行开头的写法。
- 修饰符顺序和重复在 Parser 里检查；修饰符能不能用在某种声明上（比如 `async` 只能用在函数上），在语义分析里检查。
- 区间目前只能写在 `for ... in` 后面和 `case` 里，Parser 照常把它当表达式解析，用在别处由语义分析报错。
- 错误码的列表和格式见 design/diagnostics.md。
