# ADR-0012: 命名空间与导入、函数类型与 lambda、泛型

- 状态：已接受
- 日期：2026-10-02

## 背景

第八轮讨论：每个真实脚本都会用到的命名空间与导入、lambda、泛型。C# 有全局 using 和 SDK 的隐式 using，单看一个文件不知道名字从哪来。lambda 这一项，用户提出：函数类型写成 `func(参数类型) -> 返回类型`，lambda 也以 `func` 开头，这样没有返回值时不需要 `void` 占位；以及成员函数是否也用 `let` 定义。前者采纳，后者没有采纳（理由见备选方案）。

## 决策

1. **文件结构**：开头 `namespace A.B`（一个文件最多一个，作用于整个文件，同 C# 的文件级命名空间；不写时在全局命名空间），然后是 `import`，然后是声明。顺序固定。
2. **导入**：`import 命名空间`，导入整个命名空间。
   - 每个文件显式列出自己的导入，没有全局导入，也没有隐式导入。
   - 内置类型名（`int`、`string` 等）不用导入。外层命名空间里的类型按 C# 的规则可见。
   - 漏了导入时，诊断给出该类型所在的命名空间和要加的那一行。
3. **函数类型**：`func(A, B) -> R`；没有返回值写 `func(A, B)`，没有 `void`。
   - 翻译成 .NET 的 `Func<>` / `Action<>`，和 C# 里的同类委托是同一个 CLR 类型。
   - Nyxel 代码里写函数类型统一用 `func(...)`；写 `Func<>` / `Action<>` 给警告，提示改写。
4. **lambda 是去掉名字的函数**：
   ```nyxel
   let alive = enemies.Where(func(e) = e.Hp > 0)          // 表达式体
   self.button.OnClick(func(evt) {                         // 块体
       self.clicks += 1
   })
   let nearest = enemies.MinBy(func(e: Enemy) -> float {   // 也可以写全类型
       return (e.Position - self.Position).Length()
   })
   ```
   - 参数类型和返回类型能从上下文推断时可以省略。
   - 块体里的 `return` 从这个 lambda 返回（外面写着 `func`，看得出 `return` 属于谁）。
   - 捕获外部变量的规则同 C#；方法里的 lambda 可以使用 `self`。
5. **函数的表达式体**：具名函数和 lambda 都可以写 `= 表达式`，比如 `func IsDead(self) -> bool = self.hp <= 0`。表达式的值就是返回值；没有返回值的函数，表达式可以是一个没有返回值的调用。因为赋值是语句（ADR-0011），赋值不能作为表达式体，要写成块。
6. **成员函数仍然用 `func Name(...)` 声明**，不用 `let Name = func(...)`。
7. **泛型**：
   - 类型参数写在 `<>` 里，声明和使用都同 C#：`List<Enemy>`、`World.Spawn<Slime>()`。类型实参的推断同 C#。
   - 约束写在 `<>` 里：`<T: IComparable<T>>`，冒号后面是类型（ADR-0011 的规则）。多个约束用 `and` 连接：`<T: class and IPoolable>`。
   - C# 的特殊约束照写在冒号后面：`class`、`struct`、`unmanaged`、`new()`。

## 备选方案

- **项目级全局导入**（在 .nyxelproj 里声明）：每个文件少写几行，但单看一个文件不知道名字从哪来。**`using`（同 C#，含全局和隐式 using）**：C# 程序员熟悉，但 `using` 在 C# 里还兼任“用完自动释放资源”，一词两义；隐式导入正是要避免的“看不见的规则”。
- **lambda 写成 `(e) -> 表达式`**（Java）：更短，但块体 `(e) -> { return ... }` 和 match 分支的块长得像，而两者的 `return` 去向不同（lambda 从自己返回，match 分支从外层函数返回）。**`e => 表达式`**（C#）：语言里重新出现 `=>`，函数类型还要写 `Func<>` / `Action<>`。**Swift 的 `{ e in 表达式 }`**：Agent 语料较少，`in` 和 `for` 循环里的 `in` 含义不同。
- **lambda 的表达式体写成 `func(e) -> 表达式`**：`func(...) -> X` 里的 X 本该是返回类型，读者分不清箭头后是类型还是值。用 `=`，符合“等号后面是值”。
- **函数类型写 `(Enemy) -> void`**：要多一个只在这里出现的 `void`；用户提出的 `func(Enemy)` 不需要占位，和声明的写法一致。
- **成员函数也用 `let Name = func(...)` 定义**（用户的设想，JS 风格）：概念最统一，但在 CLR 里，方法（能 override、能实现接口、引擎靠反射找到 `Update`、直接调用最快）和存放委托的字段（每个实例分配、不能 override、C# 看到的是字段）是两种东西。`let X = func...` 只能悄悄编译成方法，而 `var X: func(...) = func...` 必须是字段，长得一样含义不同；看到 `let` 也要读到 `func` 才知道声明的是函数。JS、Lua 能统一是因为它们是动态语言。
- **泛型约束写在 `where` 子句里**（C#）：长签名时整齐，但约束离类型参数远。**泛型用 `[T]`**（Go、Scala）：没有和小于号的解析歧义，但和所有 .NET 代码的 `List<int>` 不一致，也和下标长得像。

## 后果

- “lambda 就是没有名字的函数”：同一套写法，读者只需要认一种。
- 每个文件的依赖都写在开头，Agent 改代码时也能看到哪些命名空间可用。
- `<` 的歧义（泛型还是小于号）由语法分析器按 C# 的规则消解。
- 待定：导入别名、静态导入（C# 的 `using static`）；泛型的可空性（`T?` 在 class / struct 两种 T 下的含义）；泛型接口的协变 / 逆变（`in` / `out`）；属性 getter 的表达式体。
