# ADR-0028: ADR 保持最新：被推翻的决定改写原文，文末记修订

- 状态：已接受
- 日期：2026-10-16

## 背景

规则原来是“不改已合进 main 的 ADR”：决定变了就写新 ADR，在新 ADR 里写明取代旧的哪一条。用户问从后面开发顺利的角度，ADR 应不应该改。实际出现了三个问题：

- **旧 ADR 看不出自己过时了。** 全部 ADR 的状态都是“已接受”。ADR-0013 里还是 `super.init(...)`，ADR-0009 的默认分支还是 `else`；人或 Agent 直接打开旧 ADR，会照旧写法写。只有新 ADR 指向旧的，旧的不指向新的。
- **事实性的引用会失效或写错。** ADR-0002 写“整理进 master（CLAUDE.md “提交”）”，分支 2026-10-05 改名 main，CLAUDE.md 2026-10-15 改名 AGENTS.md。ADR-0026 把 ADR-0011 的决策 2（属性）写成了决策 3。
- **规则自相矛盾。** AGENTS.md 说不改；coding-conventions 说“旧 ADR 标‘被取代’，不改历史”；ADR 模板的状态一栏有“被 ADR-YYYY 取代”，而这只能回去改旧文件才标得上。

先按推荐做了“正文不改、只加标注”（状态一栏写哪部分被取代，被取代的决定下面加一行引用块）。用户看了提出：标注多了像打补丁；以后会有链式取代；既然有版本管理，历史就交给 git，ADR 描述最新的情况，决定被推翻这件事用合适的方式记下来。

## 决策

ADR 保持最新。

1. **决定被推翻时，直接把原文改写成现在的规则，例子也一起改。** 所有写过这条决定的 ADR 都改，用 grep 找旧写法。
2. **原来的做法挪进“备选方案”**：写明是原来的决定、什么时候为什么改掉、在哪个 ADR 讨论的。只是例子里顺带用到的写法（当时没有比较过）直接改，不进备选方案。
3. **文末加“修订记录”一节**，每次修订一行：日期、改了哪条决定、讨论在哪个 ADR。状态写“已接受（最近一次修订的日期 修订）”。
   ```markdown
   - 状态：已接受（2026-10-15 修订）
   ...
   ## 修订记录

   - 2026-10-15：决策 2 的写法由 `super.init(...)` 改为 `init super(...)`，规则不变，见 ADR-0027。
   ```
4. **新一轮讨论照常写新 ADR**，记录这一轮比较了什么、为什么；后果里写明改了哪些旧 ADR 的哪条。它自己以后也按 1–3 保持最新。
5. **路径、文件名、分支名、编号这类引用失效或写错时直接改**，不算修订，不写修订记录。
6. **“待定”不回头更新**：它是当时的问题清单，不会让人照着写错，现在还没定的看 language-reference 和 STATUS。同一个 ADR 的决定改写后和它自己的待定直接矛盾的，一起改。
7. 原文的历史在 git 里：`git log -p -- docs/decisions/0013-*.md`。
8. dev 上还没合并的 ADR 不算定案，推翻时照旧直接改，不写修订记录。

本轮把已有的都改成最新：

- 新 ADR 里写明了改动的：0001（npm scope，0018）、0007 决策 4（0025）、0009 决策 5、6、7（0024、0025、0026）、0011 决策 2（0026）、0013 决策 2（0027）、0014 决策 4（0025、0026）、0015 决策 3（0025）、0019 决策 2（0026）、0020 决策 6（0025）。
- 当时没写明、这次查例子找到的：0008 决策 2、4 的 case 数据是小写（0024 改成 PascalCase），决策 3 命名 init 的构造函数是私有的（0027 改成对子类可见）；0010 决策 6 的 `case Burn(seconds)` 是按名字取数据（0024 改成按位置）；0024 决策 3、8 的 `else` 默认分支（0026 改成 `case _`）。0018、0024–0027 后果里“已合进 main，不改原文”的说法跟着改了。
- 只改引用：0002 的分支名和文件名；0026 的决策编号；0025 备选方案里“`match` 里有 `else ->`”。

## 备选方案

- **完全不改**（原规则）：最严格，改过什么一目了然；但上面三个问题随着 ADR 增多越来越严重，读者要先知道“去找后面的 ADR”。
- **正文不改，只加标注**（先做了这个）：状态一栏写哪部分被取代，被取代的决定下面加一行 `> 被 ADR-XXXX 取代：…`。正文还是旧写法，读者要自己把标注叠上去；ADR-0009 一份就有三处标注，越积越像补丁；标注里写了“新的是什么”，那句话再被推翻时又过时，读者得 0013 → 0027 → 下一个一路跳（用户指出）。
- **只在索引里记取代关系**：维护最省，但旧 ADR 本身没有任何提示，直接打开还是会照着写。
- 选保持最新：打开哪个 ADR 都是现在的规则；没有链，每个 ADR 都是最新的，修订记录指向的 ADR 也是；正文不插补丁，修订集中在文末；最有用的那部分历史（原来为什么那样选、为什么改掉）留在备选方案里。代价：推翻一条决定时要改写所有写过它的 ADR；原文要到 git 里看。传统上 ADR 不改是怕丢掉当时的理由，这里理由挪进了备选方案，原文 git 里有，读 ADR 的主要是 Agent 和改设计前的维护者，过时的正文对他们有害。

## 后果

- AGENTS.md 的“改决定”、coding-conventions 的“文档”一节、ADR 模板的状态一栏、docs/README 改成这套说法；docs/README 索引里各 ADR 的描述写现在的规则，去掉“（被 ADR-XXXX 取代）”这类注记。
- language-reference 仍是“现在是什么”的完整描述；ADR 的决定和它一致，多了“为什么”。
- 推翻旧决定的那一轮要多做一步：搜一遍所有旧 ADR（包括例子）里的旧写法。这次就查出了三处当时没列的。
