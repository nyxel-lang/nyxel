# ADR-0004: 编译模型：自研前端，后端翻译成 C# 交给 Roslyn

- 状态：已接受
- 日期：2026-10-02

## 背景

CLR 只执行 IL 程序集，任何 .NET 语言都要产出 IL。编译器分五步：词法分析、语法分析、语义分析、降级、代码生成（IL + PDB 调试符号）。前两步只和语法有关；后三步是大头：.NET 泛型、重载决议、闭包、协程状态机、调试符号。

约束：游戏代码每帧执行，性能要接近 C#；要和 C# 双向互操作；断点要能打在 .nyxel 上；要支持热重载；项目规模是个人加 Agent。

## 决策

- **前端自研**：Lexer → Parser → 语法树 → Binder（名字解析、类型检查、Nyxel 的语义规则）。Nyxel 的错误由前端报出，用 Nyxel 的术语，带稳定错误码和 .nyxel 位置。
- **后端借 Roslyn**：把绑定后的树降级成 C#，交给进程内的 Roslyn（`Microsoft.CodeAnalysis.CSharp`）编译出 .dll + portable PDB。C# 是用列跟踪的文本写出器生成再解析，还是用 SyntaxFactory 直接构造语法树，M2 设计降级时定。验证结果倾向前者，因为 `#line` 的列偏移需要知道每条语句生成在第几列（design/debug-mapping.md）。
- **调试映射**：生成的 C# 带 `#line (行, 列) - (行, 列) "文件.nyxel"` 跨度指令（C# 10 起支持，Razor 就是这么做的），PDB 里记录的是 .nyxel 的位置：断点、单步、异常堆栈都对应 .nyxel 源码。
- **Roslyn 的诊断是兜底**：映射回 .nyxel 位置后报出，同时标为编译器内部错误。出现一次说明前端漏了一项检查，要补上。
- **翻译结果可见**：`nyxel build --emit-cs` 输出生成的 C#。测试用它做快照：.nyxel 输入 → 生成的 C# 与预期逐字比较。
- **后端留接口**：如果将来某个特性用 C# 表达不了，那一块单独生成 IL。不预先实现。

## 备选方案

- **解释执行**：运行时遍历语法树执行，不生成 IL。热重载最简单，但比编译执行慢 10 到 100 倍，调 C# 要走反射，现成的 .NET 调试器看不到脚本。每帧运行的游戏逻辑不适合。
- **自己生成 IL**（C#、F# 编译器的做法）：语义完全自由，但泛型、闭包、协程状态机、PDB 都要自己写，个人项目要做到能用以年计。
- **作为 C# Source Generator**：.nyxel 作为 AdditionalFiles 放进 csproj，由生成器在 C# 编译时翻译。接入 `dotnet build` 零成本，但 Nyxel 永远寄生在 C# 项目里，编译时序和诊断受 C# 编译器支配，进程内快速热重载也用不上。

## 后果

- 好处：最快能跑起来，精力集中在语言设计上；生成的 C# 人和 Agent 都能直接读，调试编译器很方便；宿主进程里常驻 Roslyn，热重载编译是几十毫秒的量级（不用起 `dotnet build`）；语言服务器可以借 Roslyn 的语义模型拿到 .NET 类型信息；产物是普通程序集，C# 能引用，能 NativeAOT 发布。
- 限制：Nyxel 的语义只能是 C# 能表达的。C# 很丰富，现代语言特性基本都能翻译过去，每个特性定稿时都要写出它对应的 C#。
- 依赖：Nyxel.Compiler 依赖 Roslyn（约 10 MB）。第一次编译要 JIT 预热，约 1 到 2 秒，常驻后快。Nyxel.Host 做进程内编译时 Roslyn 会进到游戏进程，只在开发期这样；发布时用预编译的程序集。
- 调试器的监视窗口和即时窗口按 C# 求值：PDB 里 .nyxel 文档的语言标记是 C#。
- 验证（2026-10-02）：手写带 `#line` 的 C# 经进程内 Roslyn 编译，PDB 序列点、异常堆栈、Roslyn 诊断都指向 .nyxel，前提是遵守 design/debug-mapping.md 的生成规则。真实调试器停断点（VSCode 扩展已声明 `contributes.breakpoints`）放到 M2 验收时手动验证。
